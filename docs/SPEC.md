# 허니문닥터 (Honeymoon Doctor) — 원본 스펙

> 이 문서는 2026-08-05 사용자가 제시한 원본 요구사항 전문을 그대로 보존한 것이다.
> 구현 중 스펙 해석이 필요할 때는 이 문서를 1차 근거로 삼는다. 진행 상황·설계 결정·
> 다음 단계는 [PROGRESS.md](PROGRESS.md)를 참고한다.

당신은 시니어 Android 엔지니어이자 보안·테스트에 강한 QA 친화적 제품 개발자다. 계획이나 코드 조각만 제시하지 말고, 현재 저장소를 먼저 확인한 뒤 실행 가능한 프로젝트를 실제로 구현하라.
기존 파일과 사용자의 변경사항은 보존한다. 빈 저장소라면 Android 프로젝트를 생성하고, 기존 저장소라면 구조·빌드 도구·의존성·규칙을 먼저 파악한 뒤 최소 침습적으로 확장한다.
작업 중 외부 설정값이 없어 막히는 부분은 안전한 데모 모드로 구현·검증하고, 최종 보고에 사용자가 직접 넣어야 할 설정만 명확히 남긴다. 구현하지 않은 기능을 구현한 것처럼 표현하지 않는다.

# 1. 프로젝트 정의
* 앱 이름: **허니문닥터**
* 영문 표기: `Honeymoon Doctor`
* 패키지명: `com.jeongmin.honeymoondoctor`
* 한 줄 소개: **정민·찬희 신혼여행 전담 주치의**
* 플랫폼: Android 네이티브 앱, APK 직접 설치
* UI 언어: 한국어 우선
* 사용자: 부부 2명
* 운영비 조건: 월 0원 유지
* 목표: 여행 일정 과밀, 예약 누락, 준비물 미비, 예산 초과를 한 화면에서 확인하고 대응하는 공동 여행 운영 앱
핵심 UX 목표는 현지에서 앱을 열고 **10초 안에 다음 일정, 이동, 예약, 할 일, 근처 후보**를 판단하는 것이다.
"닥터" 세계관은 상태 문구에만 가볍게 사용한다. 실제 의료 서비스처럼 보이거나 과하게 유치하게 만들지 않는다.
예시 문구:
* `오늘의 처방: 프라하 구시가지 도보 이동으로 충분합니다.`
* `주의 증상: 확인이 필요한 예약 2건`
* `과로 경고: 일정 2건의 시간이 겹칩니다`
* `여행비 출혈: 쇼핑 예산을 12% 초과했습니다`

# 2. 절대 제약과 범위
1. Kotlin + Jetpack Compose + Material 3으로 구현한다.
2. Firebase는 Firebase Authentication과 Cloud Firestore만 사용한다.
3. Firebase Storage, Cloud Functions, 유료 Google Maps/Places API, 실시간 항공·환율·날씨 API, Google Maps 저장 목록 크롤링은 사용하지 않는다.
4. 길찾기는 Google Maps 외부 Intent만 사용한다. API 키를 요구하지 않는다.
5. Google Maps 즐겨찾기는 자동 동기화하지 않는다. 수동 추가와 TSV/JSON 가져오기만 지원한다.
6. 위치는 화면 진입 또는 Pull-to-Refresh에서만 취득한다. 백그라운드 위치 추적은 금지한다.
7. Firebase 설정이 없는 개발 환경에서도 데모 모드로 앱이 정상 실행·테스트되어야 한다.
8. 비밀키, 서비스 계정, 토큰, 예약번호, PIN, 여권 정보, 카드번호를 코드·Git·분석 로그에 남기지 않는다.
9. 바우처 파일은 **각 기기 안에서만** 저장·열기한다. 부부 간 파일 동기화는 이번 MVP에서 구현하지 않는다.
10. 바우처 원본·파일명·파일 메타데이터를 Firestore에 저장하지 않는다.
11. P0 기능을 모두 마치기 전 P1 확장 기능을 만들지 않는다.
이번 MVP에서 제외할 P1 기능:
* 바우처 파일의 부부 간 동기화
* 자동 환율·날씨·항공 상태 수집
* Google Maps 저장 목록 자동 읽기
* 실시간 위치 공유
* 여행사·결제·예약 서비스 연동
* 웹 또는 iOS 앱

# 4. 데이터 편집 정책 — 매우 중요
초기 여행 정보는 하드코딩된 읽기 전용 정보가 아니다. **여행 생성 시 한 번만 삽입되는 수정 가능한 시드 데이터**다.
* 시드 데이터는 최초 여행 생성 시에만 삽입한다.
* 앱 업데이트, 재실행, 동기화 시 시드 데이터를 다시 덮어쓰거나 중복 생성하지 않는다.
* 모든 운영 데이터는 권한 범위 안에서 생성·조회·수정·삭제(CRUD)할 수 있어야 한다.
* 대상: 여행 기본정보, 도시, 일정, 예약, 준비물, 경비, 예산, 장소, 결정함.
* 소유자만 여행명, 기간, 구성원, 초대코드, 여행 삭제를 변경할 수 있다.
* 두 구성원 모두 일정·예약·준비물·경비·예산·장소·결정함을 CRUD할 수 있다.
* 삭제 전 연결된 일정·예약·경비·장소 수를 보여준다.
* 연결 데이터는 자동 연쇄 삭제하지 않는다. 사용자가 확인하면 참조를 해제한 뒤 삭제하거나, 삭제를 취소할 수 있게 한다.
* 예약 삭제 시 연결된 기기 바우처도 삭제할지 별도 확인한다.
* 데모 모드에는 `데모 데이터 초기화` 메뉴를 제공한다. 실제 Firestore 여행 데이터에는 자동 초기화를 제공하지 않는다.
* 시드 데이터에 없는 장소·예약번호·주소·좌표·평점·후기를 임의로 생성하지 않는다.

# 7. P0 기능 상세

## 7-1. 인증 및 2인 공유
* Google 로그인
* 새 여행 생성
* 여행명, 기간, 기본 통화 설정
* 소유자가 초대코드 생성·재발급·만료 처리
* 초대코드를 받은 파트너가 참여 요청
* 소유자가 승인 또는 거절
* 승인 후 최대 2명까지 구성원 등록
* 로그아웃, 동기화 상태, 데모 모드 상태 표시
초대 보안 요구사항:
* 초대코드 원문은 Firestore에 저장하지 않는다.
* 충분히 긴 난수 기반 초대코드를 생성한다.
* Firestore에는 SHA-256 해시만 저장한다.
* 파트너의 참여 요청은 초대코드 해시 일치 여부를 Rules에서 검증한다.
* 초대코드에는 여행 ID와 충분한 난수 비밀값을 포함할 수 있다.
* 참여 요청이 승인되기 전에는 해당 사용자가 여행, 일정, 예약, 지출, 장소 데이터를 읽지 못해야 한다.
* 승인 시 소유자가 트랜잭션 또는 배치 작업으로 구성원 문서와 `memberIds`를 일관되게 갱신한다.
* Security Rules의 `getAfter()` 등을 사용해 최대 2명, 소유자 유지, 승인된 구성원만 접근 가능함을 보장한다.
* 클라이언트의 역할 체크만 믿지 말고 Firestore Rules에서 강제한다.

## 7-2. 홈 — 오늘의 진료
출발 전 홈:
* 출발 D-day
* 미완료 필수 준비물 수
* 확인 필요 예약 수
* 총예산, 현재 지출, 잔여액
* 빠른 실행: 지출 추가, 예약함, 준비물, 주변
여행 중 홈:
* 현지 날짜, 도시, 현지 시간, 한국 시간
* 가장 가까운 다음 일정 — 화면에서 가장 크게 표시
* 다음 일정까지 남은 시간
* 이동 일정이면 출발 권장 시각
* 오늘 타임라인
* 오늘의 필수 확인 카드
* 오늘 지출과 잔여 예산
* 오프라인 상태, 마지막 동기화 시각, 동기화 대기 변경 수
다음 일정 계산 규칙:
* 현재 시각 이후 가장 빠른 미완료 일정이 다음 일정이다.
* `allDay` 일정은 시간 일정과 구분해 표시한다.
* 일정 저장 시 지정한 시간대를 기준으로 표시하고, Firestore에는 UTC Timestamp로 저장한다.
* 프라하 → 바르셀로나, 마드리드 → 인천 등 시간대가 달라지는 항공 일정의 시작·종료를 정확히 처리한다.
* 자정 경계, 앱 백그라운드 복귀, 네트워크 전환, 기기 시간대 변경 시 재계산한다.
* 중요 일정은 24시간, 3시간, 1시간 전 상태를 다르게 표시한다.

* 파일당 최대 15MB, 기기 총합 최대 100MB
* 파일은 앱 내부 저장소에 복사하고 FileProvider로 연다.
* 바우처 원본과 파일명·경로·메타데이터는 해당 기기에만 저장한다.
* Firestore에는 바우처 존재 여부 같은 동기화 불가능한 기기 상태조차 저장하지 않는다.
* 다른 기기에서는 `이 기기에 저장된 바우처 없음`으로 분명히 표시한다.

* 도시
* 카테고리
* 위도·경도
* Google Maps URL
* 우선순위: 꼭 가기, 가고 싶음, 여유 시
* 개인 메모
* 방문 여부와 방문 시각
* 평점·리뷰 수 스냅샷
* 스냅샷 확인일
* 추천 시간대: 오전, 점심, 오후, 저녁, 밤, 언제나
* 마지막 수정 시각
동작:
* 화면 진입 시 Firestore 최신 장소와 최근 위치를 반영한다.
* Pull-to-Refresh 시 위치를 강제 갱신하고 재정렬한다.
* 위치 권한 거절 시 현재 선택 도시 기준으로 표시하고, 거리 계산이 불가능한 상태를 분명히 알린다.
* 호텔 또는 도시 기준 좌표가 사용자가 입력돼 있으면 그 기준으로 정렬한다.
* 오프라인에서는 마지막 캐시와 최근 위치 기준으로 보여준다.
* 필터: 전체, 맛집, 카페, 관광, 쇼핑, 숙소, 미방문만
* 정렬: 거리순, 추천순
* 상위 3개를 `지금 가기 좋은 처방`으로 크게 표시한다.
* 각 장소에 직선거리, 우선순위, 방문 여부, 메모, 길찾기 버튼을 제공한다.
* 길찾기는 Google Maps 외부 Intent로 열고, 앱이 없으면 브라우저로 안전하게 대체한다.
* 좌표 없는 장소는 목록에서 삭제하지 않고 `위치 미확인` 섹션에 둔다.
* TSV/JSON 가져오기 전 미리보기, 유효성 검증, 오류 행 안내, 중복 확인, 가져오기 결과를 제공한다.
거리 계산:
* Haversine 공식으로 기기 로컬에서 계산한다.
* 장소 좌표 또는 현재 위치가 없으면 거리값을 임의로 표시하지 않는다.
추천 점수는 기기 로컬에서 계산하고 점수 근거를 사용자에게 보여준다.
* 거리 적합도: 최대 45점
* 현재 도시·오늘 일정 적합도: 최대 20점
* 개인 우선순위: 최대 15점
* 시간대 적합도: 최대 10점
* 평점·리뷰 수 스냅샷: 최대 10점
세부 규칙:
* 거리 점수는 300m 이하 45점, 1km 이하 35점, 2km 이하 25점, 5km 이하 10점, 그 이상 0점으로 구현한다.
* 현재 도시와 일치하면 20점, 선택 도시와만 일치하면 10점, 그 외 0점이다.
* 우선순위는 꼭 가기 15점, 가고 싶음 9점, 여유 시 4점이다.
* 추천 시간대가 현재 시간대와 일치하면 10점, `언제나` 또는 미입력이면 5점, 불일치하면 0점이다.
* 평점·리뷰 수가 없으면 해당 항목은 0점이며, 점수 신뢰도 낮음 상태를 표시한다.
* 평점·리뷰 수는 실시간 수집하지 않으며, 사용자가 가져오거나 직접 입력한 스냅샷만 사용한다.

## 7-8. 오프라인과 알림
* Firestore 오프라인 캐시를 사용한다.
* 마지막 동기화 시각, 오프라인 상태, 동기화 대기 변경 수를 보여준다.
* Firestore가 정확한 대기 변경 건수를 직접 제공하지 않는 부분은 앱의 로컬 변경 큐로 추적한다.
* 중요한 일정의 24시간, 3시간, 1시간 전 로컬 알림을 지원한다.
* Android 13 이상에서 알림 권한을 거절해도 앱의 핵심 기능은 정상 동작해야 한다.
* 권한 거절 시 설정 안내만 제공한다.
* 정확한 알람 권한이 없으면 WorkManager 기반 비정확 알림으로 안전하게 대체한다.
* WorkManager 알림은 지연될 수 있음을 코드·문서에서 정확히 다룬다.

# 9. Firestore 보안 요구사항
반드시 `firestore.rules`를 작성한다.
* 인증되지 않은 사용자는 모든 접근을 거부한다.
* 전체 여행 목록 조회는 금지한다.
* 로그인 사용자는 자신의 UID가 `memberIds`에 포함된 여행만 조회할 수 있다.
* 여행 구성원만 해당 여행과 하위 컬렉션을 읽고 수정할 수 있다.
* 참여 요청 생성은 초대코드 해시 일치와 본인 UID 조건을 동시에 충족해야 한다.
* 참여 요청자는 승인 전 여행 본문이나 하위 컬렉션을 읽지 못한다.
* 소유자만 초대 승인·거절, 구성원 변경, 초대코드 변경, 여행 기본정보 변경을 수행한다.
* 구성원 수는 2명을 초과할 수 없다.
* 소유자는 구성원 목록에서 제거될 수 없다.
* 일반 구성원은 자신의 권한을 소유자로 승격하거나 다른 사용자를 구성원으로 추가할 수 없다.
* 모든 하위 컬렉션 규칙은 상위 여행의 구성원 여부를 직접 검증한다.
* Firestore Emulator 테스트로 소유자, 구성원, 비구성원, 승인 전 참여자 각각의 허용·차단 흐름을 검증한다.
Firebase Analytics, Crashlytics 등 분석 SDK는 추가하지 않는다. 예약번호, PIN, 바우처 파일명, 지출 상세는 어떤 로그에도 남기지 않는다.

# 10. UI·UX 원칙
* 따뜻한 아이보리 기반, 딥 네이비를 기본색, 코랄을 경고·강조색으로 사용한다.
* 과한 웨딩 앱보다 프리미엄 여행 운영 보드 느낌을 만든다.
* 홈의 가장 큰 요소는 다음 일정이다.
* 최소 터치 영역은 48dp다.
* 한국어 긴 문구, 긴 예약명, 유럽식 긴 주소에서 잘림·겹침이 없어야 한다.
* 빈 상태, 로딩, 오류, 권한 거절, 오프라인 상태를 모든 핵심 화면에 제공한다.
* 다크 모드를 지원한다.
* 아이콘 버튼과 핵심 정보에 TalkBack용 `contentDescription`을 제공한다.
* 예약번호와 PIN은 기본값이 가려진 상태여야 한다.
* 긴급상황 화면에는 의료 조언을 생성하지 말고, 현지 긴급전화·대사관 연락처를 사용자가 직접 추가할 수 있는 구조만 제공한다.
